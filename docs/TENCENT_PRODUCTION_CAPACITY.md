# 腾讯云正式主机 1500 人实测与公网瓶颈定位

测量日期：2026-09-28。**当前 4 核 / 4GB / 5Mbps 套餐未通过 1500 人容量验收；本轮首先暴露的是公网回程瓶颈，没有证据证明 CPU 持续饱和。** 双端抓包及两条不同公网线路的吞吐对照，强烈支持服务器共享公网出口带宽限制是主要原因。尚未取得腾讯云平台侧限速丢包指标，因此不将具体丢包设备写成已确认事实。

## 版本、环境与隔离范围

- 应用版本：`81adef2bfa4441fc54d014f445e1f81383242a13`；驱动提交：`2766808`。本轮未修改业务代码。
- 应用 Python 模块组合 SHA256：`1b1ad6ec212d94e7328f7c4170cc27bcf24acb8085e0b03c73896dcd06ae84f1`。
- 实际腾讯云生产主机，4 vCPU、约 4GB，4 个 API worker + 1 个后台 worker，原生 systemd / Nginx / MySQL / Redis；使用正式域名及有效 HTTPS 证书。
- 用户套餐截图确认：SSD 云硬盘 60GB、月流量包 500GB、**公网带宽 5Mbps**。此前“10Mbps 或以上”的口头估计被本次截图更正。
- 发压机为独立 Linux 主机，网线连接普通直连路由；三个发压进程各负责 500 人。正式业务压测流量不经过 Mac、Surge 或 WireGuard。
- 用户明确授权在正式主机压测后，先备份正式库，再暂时切换到独立合成测试库、Redis DB2/测试前缀和测试文件目录；正式库没有写入压测数据。测试结束已恢复生产配置。
- 预置 3000 个合成账号、42 个社团；每轮业务压力为 1500 个独立账号，其他账号用于校准。社团详情包含约 680 字中文介绍，无头像下载。
- 每人独立 HTTP 连接池及 WebSocket，真实 TLS；冷登录计划在 0.6 秒窗口发起，客户端超时 10 秒。流程包括登录、首页、详情、报名、结果确认和持续查询；不是只打登录单接口。

|---|---:|---:|---:|---:|---:|
| 冷登录第 1 轮 | 306 / 1500 | 306 | 10.018 秒 | 0.475 / 1.747 秒 | 619 |
| 冷登录第 2 轮 | 256 / 1500 | 256 | 10.009 秒 | 0.456 / 1.691 秒 | 605 |
| 冷登录第 3 轮 | 377 / 1500 | 377 | 10.015 秒 | 1.341 / 7.173 秒 | 378 |
| 提前登录、持续 10 分钟 | 448 / 1500 | 448 | 不在测量段 | 1.106 / 1.205 秒 | 749 |
| 热门社团 100 席 | 758 / 1500 | 100 | 不在测量段 | 1.580 / 1.591 秒 | 826 |
| 争抢最后 1 席 | 819 / 1500 | 1 | 不在测量段 | 0.670 / 0.824 秒 | 811 |

“完成”包含收到明确已满等正常业务结果；不等于全部报名成功。三轮冷登录分别有 834、839、1115 次登录超时。第 1 轮另有 355 人首页失败、5 人详情失败；这些不是只有少数人的性能尾部问题。报名百分位只覆盖实际进入报名阶段的请求，不能当作 1500 人同时报名已经通过。

六轮数据库核对均无名额不一致、超卖或重复占位。均匀场景原始 `data_correct` 门槛还要求预期全员报名，因此为 false；它与 `data_consistency_pass=true` 含义不同，原始字段保留。热门场景另有 1 次报名超时；没有使用大量 429/503 将压力拒绝掉来达标。

10 分钟场景实际持续 601.05 秒，结束仅 749 条 WS，出现 246 次非预期关闭；报名请求头实际发出跨度 8.05 秒，未达到 1 秒集中提交条件。20 秒后 21,312 次详情/名额查询全部 200，P95 约 20ms，但通知 P95 为 3.796 秒，超过 3 秒目标。**此项仅证明存活和部分已连接用户的持续查询稳定，不证明 1500 人在线通过。**

第 1 轮冷登录结束后，不重置报名数据，对剩余 1194 人逐个显式重试，全部完成，总报名数达到 1500，重试流程 P95 约 103ms。首次重试开始于突发后的约 70.6 秒；这不是测出的最短恢复等待时间，也不是客户端自动恢复的证明。其余两轮没有逐人补测恢复。

## 连接阶段定位

同一 Linux 发压机进行三组 1500 条冷连接诊断，均保留失败记录：

| 诊断 | 成功 | 超时分布 | 成功响应的服务端处理 P95 |
|---|---:|---|---:|
| 仅 TLS，不调用业务 | 1237 / 1500 | TLS 阶段 263 | 不适用 |
| HTTPS 健康检查 | 1109 / 1500 | TCP 33、TLS 345、响应头 13 | 0.24ms |
| HTTPS 登录单接口 | 1039 / 1500 | TLS 439、响应头 22 | 21.18ms |

健康检查同样大量超时，且主要发生在 TCP/TLS 阶段，说明不能把问题归因于密码匹配或报名 SQL。完整流程第 1 轮成功登录的应用处理 P95 为 93.6ms，客户端连接/TLS P95 为 9.393 秒；两者是不同样本和阶段的百分位，不能直接相加减计算“网络耗时”。

在服务器本机通过相同 Nginx/TLS 发起 1500 条健康请求，**1500 全部成功，端到端 P95 1.882 秒，P99 1.964 秒**。本机发压与服务共享 CPU，只用于绕过公网路径的对照，不作为独立发压的业务容量验收。

另将相同 TLS 健康请求复用一条 SSH 隧道，1263 成功、237 超时；全部完成 TCP/TLS，但仍有响应等待。这没有证明隧道能解决容量问题：它仍共享公网带宽，并引入单 TCP 队头阻塞及 SSH 通道调度开销。隧道已关闭。

### 双端 SYN 抓包

两端同步记录 SYN/SYN-ACK，使用初始序列号匹配连接。时钟校准误差约毫秒级，两端抓包内核丢包均为 0；没有捕获业务正文。地址、端口和原始序列号已从 Git 证据中移除。

| 阶段 | 客户端首个 SYN 到服务器 P95 | 服务器首个 SYN-ACK 到客户端首次收到 P95 |
|---|---:|---:|
| 仅 TLS | 8.26ms | 5.101 秒 |
| HTTPS 健康 | 6.95ms | 5.129 秒 |
| HTTPS 登录 | 6.26ms | 5.137 秒 |

三组的 1500 个初始 SYN 全部到达服务器，去程没有一个超过 200ms。仅 TLS 组服务器捕获到 3861 个 SYN-ACK（含重传），客户端只捕获到 1502 个；大量包在服务器发出后的公网回程中丢失或等待重传。这里的回程时间包含重传等待，不等于某一个包在队列里停留 5 秒。

**更正早期判断：** 不完整抓包窗口曾导致“去程 SYN 丢失”的临时推断，完整配对样本不支持它，以本节结果为准。也没有证据支持固定 1500 条 TCP / 750 条 WS 上限：当时新增少量公网连接仍能成功，后续场景 WS 超过 750。

内核监听队列 `ListenOverflows`、`ListenDrops`、`TCPBacklogDrop` 增量均为 0。整个业务监测窗口 TCP 重传增量 112,860、SYN 重传 15,144；这些是整机窗口计数，包含监控/管理连接，不能当成纯业务单次丢包率。

### 不同公网来源的吞吐对照

两台不同公网来源的机器，从服务器 SSH 下载不可压缩随机数据，数据直接丢弃，不访问业务接口。每条流 4MiB，先分别测量，再并行测量：

| 发起端 | 单独运行 | 同时运行 |
|---|---:|---:|
| Mac 公网线路 | 5.210Mbps，6.44 秒 | 2.993Mbps，11.21 秒 |
| Linux 发压线路 | 5.132Mbps，6.54 秒 | 2.331Mbps，14.40 秒 |

并行测试从启动至最后一条流结束的总吞吐为 **4.641Mbps**。两条流完成时刻不同，不能简单相加各自全程平均值当作严格同时瞬时吞吐。小样本、协议开销和短时突发会造成与名义 5Mbps 的偏差。

两条独立来源都受相近上限约束，竞争时带宽又被共同分配；结合 5Mbps 套餐、双端抓包和服务器自访公网偶发超时，**服务器共享公网出口限制比单一发压机 CPU、Mac Surge 或发压机路由连接数限制更符合证据**。精确到腾讯云限速节点仍需平台“出网超限丢包”等指标或升级带宽前后对照，不能仅用 SSH 抓包断言。

腾讯云官方说明，内地轻量实例套餐带宽指公网出方向上限，流量包是月度出流量额度，两者不同；套餐带宽也不作为强保障指标：[轻量应用服务器基本概念](https://cloud.tencent.com/document/product/1207/79254)。500GB 月流量包不能解除 5Mbps 的瞬时瓶颈。

## CPU、内存与存活

连续监测约 1724.82 秒，共 345 个有效采样，约每 5 秒一次。

- 五项服务（API、worker、MySQL、Redis、Nginx）合计最高区间 CPU：**1.429 核**，相当于 4 核容量的约 35.7%。此前报告的 **1.13 核只对应第一轮冷登录观察窗口**，不是整轮诊断的最大值。
- 合计最高区间：API 1.026 核、MySQL 0.248、Nginx 0.113、worker 0.028、Redis 0.014。
- `/proc/stat` 整机执行 CPU 区间峰值约 **1.627 核**，包含其他进程、内核和中断，排除 idle/iowait/steal；iowait 单独峰值约 0.791 核等效，steal 观测为 0。不同指标峰值不一定在同一区间，不能直接相加。
- 5 秒平均会平滑短时尖峰，也不能排除某一核短暂饱和、锁等待或磁盘等待。未采集逐核高频火焰图，因此不声称 CPU 和数据库完全没有优化空间。
- 最低可用内存约 **1799MiB**，Swap 已用最高约 0.51MiB。API 峰值 376MiB、worker 55MiB、MySQL 695MiB、Redis 9MiB、Nginx 133MiB。
- 各服务进程身份保持不变，非预期重启 0、OOM 增量 0。345 次本机健康检查全部成功；341 次公网成功、4 次公网超时。后台 outbox 最高临时积压 235，结束为 0。

1.13 核的含义是“该 5 秒内累计消耗约 5.65 CPU 秒”，并非只允许程序使用一个核。公网阻塞使许多请求根本没到应用；低 CPU 与用户超时可以同时出现。**现在能确定的是没有持续 CPU 跑满导致的崩溃，不能推导出解除网络瓶颈后 4 核一定满足全部目标。**

虚机网卡统计曾出现 37.15Mbps 的区间出流量，它是 guest 发包计数，位于云平台限速之前，不能当成用户实际收到的公网吞吐。实际传输对照约 5Mbps。

## 下一步选择

优先保持应用版本、4 核 / 4GB 和测试模型不变，调整公网带宽后复测，以隔离变量；**不建议仅凭这次结果先把 CPU 加到 8 核**。可先将 20–30Mbps 作为验证档位，再根据实测网络占用决定是否增加；这不是已验证能满足目标的配置承诺。任何付费升级须另行确认，本轮没有购买或变更套餐。

5Mbps 理论上只有 0.625MB/s，1500 人在 5 秒内平均每人仅约 2.08KB 的总下行预算，TLS 握手、HTTP 头、登录响应和首页内容都要占用它。该计算忽略协议损耗，仅说明预算量级，不代表实际每人包大小。

软件方面应优先测量并削减启动阶段的传输字节和重复连接，例如响应压缩、精简首页初始化、合并重复快照、客户端连接复用和 TLS 会话恢复；这些属于后续优化候选，本次没有修改生产代码。单纯延长超时可能减少失败，但不等于达到登录 P95≤5 秒；增加重试还可能放大拥塞。

带宽变更后重新执行三轮冷登录、提前登录集中报名、热门/最后一席、1500 WS 持续 10 分钟，再看 CPU、磁盘等待及锁等待。目标保持登录 P95≤5 秒、报名 P95≤3 秒/P99≤5 秒、通知 P95≤3 秒；正常业务拒绝与异常失败分开统计。全部请求能进入服务后才能判断是否还需要提升 CPU。
