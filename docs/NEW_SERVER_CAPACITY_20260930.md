# 新云主机部署、公网异常与私网对照

日期：2026-09-30。**新服务器已部署隔离测试版并启用可信 HTTPS，但尚未通过公网 1500 人容量验收。** 公网建连丢失和服务端突发等待是两个不同问题；私网测试成功不能替代公网验收。

## 版本与隔离

- 新主机 `43.142.19.144`，实际 4 vCPU / 8GB，EPYC 7K62，Ubuntu 22.04；用户提供公网带宽为 200Mbps。本轮没有自动购买或升级资源。该数值不等于实测持续带宽保证。
- 用户将 `wjy-1214.cloud` 解析到新主机，并放行 TCP 443。域名当前用于隔离测试部署，旧服务器和旧正式数据库未被迁移或清理。
- 应用固定 `81adef2bfa4441fc54d014f445e1f81383242a13`；Python 模块组合 SHA256 `1b1ad6ec212d94e7328f7c4170cc27bcf24acb8085e0b03c73896dcd06ae84f1`。本轮未修改业务源码。
- 运行环境是 `CLUB_ENV=test`、独立 `club_test` 库、Redis DB2 / `club:test`。只有 3000 个合成账号、42 个合成社团，详情包含约 680 个中文字符；没有导入真实学生或旧管理员。
- 原生 Nginx + 4 个 API worker + 1 个后台 worker，API 只监听 loopback 8001，以专用 `club` 用户运行。没有 CPU 配额或人工网络整形。
- MySQL 8.0.46，buffer pool 768MiB，最大连接 151；每 API 进程主池 15+3、读池 4，后台最多 10，总预算 98。保留事务持久性设置。
- Redis 7.2.16、192MiB、noeviction；Python 3.11.15，依赖按 uv.lock 导出并经哈希核验安装。下载镜像不改变锁定版本。
- Let's Encrypt RSA 证书有效至 2026-12-29，域名证书校验始终开启，保留自动续期和 Nginx reload hook。公网 `/metrics` 禁止访问，旧业务入口返回 426。

部署工具及观测提交：`88cafd7`、`7302c6d`、`50defcf`；首次改密原生驱动支持 `7edc83b`，相关 17 项隔离与观测测试通过。前端未修改。所有提交均为本地 develop，未 push。

## 部署中修复的问题

1. 公网 443 最初被云防火墙阻止，本机 HTTPS 正常。用户放行后才开始有效的公网测试。
2. Ubuntu 初始 Redis 6.0 缺少一次性 WS 票据所需的 GETDEL。升级官方 Redis 7.2 系列并修复 systemd 通知启动配置后，30 人冒烟全部通过。部署脚本已增加能力预检。[Redis GETDEL 官方说明](https://redis.io/docs/latest/commands/getdel/)
3. `/srv/club/shared` 原权限不允许 Nginx 检查维护标记，改为 0751；具体测试文件目录仍为 0750。此修复消除了维护文件权限错误，但没有解决公网 SYN 丢失。修复前后的失败记录均保留。
4. 早期测试控制 SSH 连接曾失效，该次没有形成有效容量测量；重建带保活的连接后重跑。未将准备或编排失败计入业务延迟成绩。

## 公网结果与定位

原发压机是有线 Linux `192.168.100.20`，3 个独立 Python 进程，各模拟 500 名学生。每名学生独立 HTTPS 会话，冷登录 → WS → 首页 → 社团详情 → 到点报名 → 结果确认；包含事件触发读取和在线浏览。

修复部署问题后的公网冷登录：

| 场景 | 登录 P95 | 完成全部流程 | 结果 |
|---|---:|---:|---|
| 诊断冷登录 | 2.608 秒 | 159 / 1500 | 首页连接大量超时 |
| 配对抓包冷登录 | 2.537 秒 | 166 / 1500 | 同类建连丢失 |
| 提前在线再报名 | 不在测量段 | 885 / 1500 | 结束 WS 793，出现断连 |
| 备用主机冷登录 | 3.640 秒 | 269 / 1500 | 同类失败，结束 WS 1481 |

备用主机 `192.168.100.130` 经过本机 Meta 网络栈，实际 HTTPS 出口与原发压机相同，故不是一条独立公网线路。其对照削弱了“原发压机单进程或单机限制”的解释，但不能区分共享 NAT、运营商与云侧入口。

配对抓包仅记录 SYN/SYN-ACK，不含业务正文。两端捕获窗口覆盖整个分析段、内核抓包丢包均为 0；Git 中仅保留去除 IP、端口及原始序列号后的行：

- 客户端发出 3002 个不同连接的 SYN，服务端匹配到 1667 个。
- **1335 个连接的 SYN 在服务端抓包中未出现。** 客户端重传仍未到达；失败首页请求尚未发送 HTTP 头，不能归因于报名 SQL。
- 诊断追踪显示 DNS 命中缓存，没有 connector 排队；连接未完成。原发压各分片事件循环 lag P95 约 2ms。
- 用户暂未在控制台看到告警。不能因此排除或认定云侧连接防护；也没有证据可宣称固定 1500 / 1667 连接上限。
- 腾讯云确有基于来源和目的的新建/并发连接防护机制，但文档存在不等于本实例触发了它。[官方连接防护说明](https://cloud.tencent.com/document/product/297/94678)

旧云主机还做了独立公网 HTTPS 对照，但其 5Mbps 出带宽会限制发压，因此该失败结果仅作为补充，不直接用来定位新主机的限制节点。

业务测试结束后，用同一脚本做了每组 3000 条、约 1 秒内发起的纯 TCP 建连对照（无 TLS、无业务请求，每连接最多等待 8 秒）：

| 发起端与路径 | 建连成功 |
|---|---:|
| 原局域网发压机 → 新主机公网 | 1758 / 3000 |
| 旧云主机 → 新主机公网 | 3000 / 3000 |
| 旧云主机 → 新主机私网 | 3000 / 3000 |

这进一步反对“新主机统一存在约 1700 条 TCP 上限”的解释。问题更集中在局域网出口路径，或云端针对该公网源 IP 的处理，不能仅靠现有主机抓包确定是路由器、运营商还是云侧源 IP 策略。此建连对照不包含 TLS / HTTP，不代表 3000 名用户业务容量通过。

## 私网对照的边界

由独立旧云主机向新主机私网 `10.0.0.11:443` 发压，保留相同域名、TLS 证书校验、业务应用、数据库和请求模型。仅在测试进程内指定解析地址，未修改系统 DNS、旧业务服务或数据库。

**它绕过了两台机器的公网带宽与公网入口路径，延迟也更低，结果只能说明此条件下应用的行为。** 原始报告明确标记 DIAGNOSTIC ONLY，并始终保持 `production_capacity_verified=false`。

| 私网场景 | 完成流程 / 人 | 有效报名数 | 登录 P95 | 报名 P95 |
|---|---:|---:|---:|---:|
| 同时冷登录 | 1500 | 1500 | 2.483 秒 | 3.872 秒 |
| 提前在线、均匀报名 | 1500 | 1500 | 预登录 | 4.005 秒 |
| 热门社团 100 名额 | 1500 | 100 | 预登录 | 2.577 秒 |
| 最后一个名额 | 1500 | 1 | 预登录 | 1.981 秒 |
| 10 分钟在线 | 1500 | 1500 | 预登录 | 3.702 秒 |
| 1200 在线 + 300 冷登录 | 1500 | 1500 | 2.044 秒 | 4.317 秒 |
| 集中断线重连 | 1500 | 1500 | 预登录 | 4.567 秒 |
| 首次登录、强制改密后报名 | 1500 | 1500 | 3.832 秒 | 1.961 秒 |

热门/最后名额场景的“完成”包括收到明确满额结果，不代表全部报名成功。均匀、混合、重连场景包含繁忙后的查询和幂等重试，均匀报名首次 63 次繁忙、混合 78 次、10 分钟场景 43 次、重连 36 次；初次错误单独计入失败率；**不是零错误容量通过**。这些场景均为一轮，未用重复三次不合格测试来声称三轮达标。

完整数值、请求状态分布和门槛见 `reports/new-server-capacity-20260930/summary.json`。没有把满额等正常业务拒绝算作服务错误，也没有用最终重试成功掩盖初次 503。

## 十分钟稳定性结果

私网 1500 人提前在线并同时报名，保持约 600.95 秒：

- 结束时 1500 条 WS 全部在线，意外断连 0，最终名额版本全部一致；数据库 1500 条有效报名、名额差异 0。
- 初次报名 1457 次成功、43 次繁忙，随后查询和幂等重试完成全部报名；P95 3.7019 秒、P99 3.9322 秒。该延迟及初次繁忙比例仍不合格。
- 稳态（测量开始 20 秒后）43,177 次详情/名额读取全部成功，P95 8.9ms，P99 11.9ms。这是私网延迟，不代表手机公网耗时。
- 名额通知 P95 1.3813 秒，符合放宽后的 3 秒目标。

## 已发现的服务端等待

提前在线均匀报名场景，1500 个初次报名请求中 1437 个返回成功、63 个返回 `503/TEMPORARILY_UNAVAILABLE`，查询及幂等重试后最终 1500 人成功。额外有 3 次查询 503。报名 P95 4.005 秒，未达到 3 秒目标。

应用记录 `dependency_failure type=TimeoutError`。`club/db.py` 连接池等待上限为 3 秒，`club/services.py` 报名事务在获取连接后才执行锁定和写入；`club/api.py` 将 SQLAlchemy/Redis 依赖异常统一转换为此错误码。对应测量窗口的报名取连接累计等待约 1061.57 秒 / 1563 次（包含重试），而读池累计约 19.86 秒 / 3417 次，支持主连接池等待值得优先调查。它们是累计和与次数，不能当成单请求 P95。当前日志只打印短类名，不能仅凭它排除 Redis 同名异常；后续应补充异常所属模块和连接池等待分布，再针对等待原因优化，避免只延长超时掩盖问题。

5 秒采样观测到服务合计约 3.85 核的峰值。公网请求被挡在应用之外时 CPU 较低，私网完整负载下则接近 4 核；两者并不矛盾。此平均值仍可能平滑单核或瞬时尖峰，不能直接当成硬件升级定论。

## 资源与结束状态

维护目录修复后的主要观测约 3057.62 秒、610 个采样，覆盖多场景及传输诊断，**不等于 51 分钟持续保持 1500 人**；实际持续在线场景为上文 600.95 秒。

- 服务合计 5 秒平均峰值 3.8476 核，整机执行 CPU 峰值约 3.9797 核；API 在服务峰值窗口约 2.9292 核、MySQL 0.6446 核、Nginx 0.2123 核。采样非原子且有统计更新时间差异，两个峰值不可直接相加。
- 最低可用内存 5749MiB；API cgroup 峰值约 460MiB、MySQL 737MiB。没有 Swap，OOM 增量为 0。10 分钟场景第 1 分钟之后，API 约 451.34 → 450.41MiB、MySQL 约 672.17 → 672.13MiB；Nginx 约 255.11 → 261.60MiB，增加约 6.5MiB，仍需后续更长观察才能判断是否稳定，不能据此声称已排除所有长期泄漏。
- API、worker、MySQL、Redis、Nginx 全程 active，进程身份不变、非预期重启为 0。实例自身发起的本机/公共域名健康探测各 610 次均成功，不代表外部发压路径无故障。
- outbox 采样峰值 375，结束为 0。监听队列 ListenOverflows / ListenDrops / TCPBacklogDrop 增量均为 0；整机网络重传包括测试与管理流量，不当作业务独立丢包率。
- 发压进程和临时控制连接已经停止。测试库保留 3000 个合成账号、42 个合成社团和最后一轮报名供复核，活动改为草稿并清空开放时间；公网业务入口返回维护 503，本机就绪检查 200。
- 新主机尚未切为正式生产数据配置，未创建或迁移正式管理员；不能用测试账号交付正式运营。后续正式启用应使用独立生产库、生产配置和私密交付的管理员凭据，再关闭维护。
- 旧服务器的业务服务、数据库和配置未改动；仅增加了独立测试客户端目录。测试脚本、报告留存用于复现；不自动提审或发布小程序。

发压机没有与被测服务共享 CPU；私网主要场景的发压循环 lag P95 约 1.3–1.6ms，10 分钟场景最大瞬时 lag 约 0.380 秒，实际报名突发跨度仍符合对应测试门槛。首次改密额外增加的步骤会改变报名抵达时间，不能用其较低报名延迟替代提前在线的同步开抢成绩。
