# 2026-09-30 报名链路优化后的公网复测

**结论：按用户确认的验收口径（结果正确、无报错、无崩溃，允许变慢），新版本在 4 vCPU / 8GiB 上通过服务端验收。** 首次 503 从每轮 77–152 次降为 0；9 个场景全部数据一致、无超卖、无进程重启或 OOM。报名 P95 仍约 3.8–4.1 秒，未达原定 3 秒，原因是 API 进程 CPU 饱和，用户体感为稍慢，结果不变。

用户口径（2026-09-30）：只要不出现与预期不符的结果，耗时变长可以接受。原“报名 P95 ≤ 3 秒”降为参考指标，不再作为通过条件。

## 环境

- 发压：公司 Mac mini（Wi-Fi），测试期间临时停用 Mihomo（TUN、系统代理、DNS），经公司网关直连；结束后按原版本恢复，见 `reports/retest-20260930/proxy-control.json`。
- 压测开场余量 0.3 秒（原 0.05 秒，见 `c540ce7`）。

## 优化前的定位（同日直连诊断，`81adef2`）

- 报名 503 全部是写连接池取连接超时（3 秒），测试窗口 220 条 `dependency_failure type=TimeoutError`。
- MySQL 中唯一慢的是社团行 `SELECT … FOR UPDATE`：均匀报名平均等锁 51ms，热门平均 134ms、最长 925ms；其余语句均 < 1ms，提交平均 3.4ms。
- 报名突发 5 秒内整机 390–400% CPU，其中 API 270–280%、MySQL 约 60%；锁因事务每条语句返回后等待事件循环而被拉长。
- py-spy：API CPU 中 ORM/驱动约 43%，框架路由与依赖约 22%，事件循环约 18%，JWT、日志、pydantic 各 3–4%；约 1.56 万次 ROLLBACK 对 1600 次提交（读连接归还）。
- 早前热门/最后名额轮次的首页超时：nginx 1440 次 bootstrap 全部 200、P95 0.21 秒，客户端建连 P95 7–9.5 秒；服务器 ListenOverflows/ListenDrops/SYN cookies 均为 0。属网络路径问题，不是服务端。

全程（约 41 分钟，491 次采样）：服务 5 秒平均 CPU 峰值 3.81 核（API 2.76、MySQL 0.50、nginx 0.47），各服务重启增量 0，oom_kill 0。每个场景报名数与名额核对一致。

报名 P95 差距来源：均匀报名轮 nginx 等待上游 P95 3.93 秒，应用内 Server-Timing P95 2.09 秒；约 1.8 秒发生在请求进入应用代码之前，即 API 进程 CPU 饱和下的排队，不是数据库或连接池。

混合入场和各场景零星的准备期/首页超时，失败请求卡在建连阶段而服务端处理很快，与此前结论一致，属发压端网络路径（单台 Wi-Fi 与同一出口承载 1500 人），真实学生各用自己的网络。

## 仍可做的事（均非通过条件）

- 若需把报名 P95 压到 3 秒内：升级到 8 vCPU 并将 API worker 调为 8，或对新版本再做一次采样继续降 CPU。
- 关闭 MySQL binlog（不需要主从时）可少一次提交刷盘，属服务器配置变更，未执行。
- 有线或多台云主机发压，可排除网络路径对混合入场的影响。
