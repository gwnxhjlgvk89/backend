# 有线独立发压：4 核配额 / 4GiB 稳定性复测

本次按用户最新要求，重点验证是否崩溃、卡死、名额错误，以及压力过后能否继续报名。延迟和原有性能门槛仍保留原始结果，不因放宽验收重点而改写失败数据。

## 环境与测试边界

- 发压：独立 Linux 主机 `192.168.100.20`，3 个进程、每进程 500 个独立学生。
- 被测：隔离 Linux 主机 `192.168.100.130`，父 cgroup `cpu.max=400000 100000`、`memory.max=4294967296`、Swap 0；4 个 API worker。
- 使用原来的 HTTPS 入口 `:18082`，校验测试 CA；没有临时替代 TLS 入口，没有人工带宽限速。实际发压流量走同一局域网的有线网络，不经过 Mac/Surge/WireGuard。
- 业务源码保持 `547aab2`，本次只调整 TEST 资源配额和观测工具，没有修改业务逻辑。
- 请求超时仍为 10 秒，没有用延长超时或大量 429/503 掩盖失败。驱动不包含前端新增的 GET 自动重试；单独恢复场景模拟用户明确重试登录。
- 配额限制不是腾讯云同型号物理 CPU；部分 rootless 网络辅助进程在父配额之外。结果不能直接作为任意云端 4 核套餐或公网 10Mbps 容量保证。

## 场景

1. 三轮 1500 人同时发起冷登录，随后首页、详情、报名和实时通知。
2. 1500 人已登录后集中报名，并保持 600 秒在线：每 20 秒心跳、20–40 秒浏览详情、60 秒校验名额。
3. 1500 人争抢热门社团的 100 个名额，以及争抢最后 1 个名额。
4. 另外三轮冷启动，每轮结束后不重置数据，找出未报名的合成账号，明确重试登录、首页、详情、报名及结果确认。

每轮数据库核对报名和名额；约每 5 秒观察服务 PID、启动时间、健康状态及资源计数。原始 cgroup 的历史 OOM 保留，按本轮计数增量判断，不能把历史峰值或上一次临时入口的 OOM 记成本次事故。

## 结果

本次没有观察到主服务进程重启、卡死或新增 OOM，报名数据没有超卖或重复占位。4 核配额 / 4GiB 在本次环境下能够完成集中报名并维持持续在线；仍有少量冷启动请求超时，不能宣称所有用户只需一直等待便会自动成功。

### 集中报名与持续运行

- 1500 个报名请求头实际在 **0.5991 秒**内发出，全部成功。P95 **2.4161 秒**，P99 **2.7855 秒**，最慢 **2.9539 秒**。
- 活跃观察 **601.69 秒**，结束时 **1500 条 WebSocket** 在线、零意外断线、最终名额版本全部同步。
- 开始 20 秒之后的 **43,302 次**详情/名额查询全部 HTTP 200，P95 **8.7ms**，最慢 **0.7463 秒**；通知 P95 **1.4621 秒**。
- 该场景内存采样从约 1986MiB 到 1976MiB，没有持续上涨；期间数据库、Redis 可用，抽样待投递通知为 0。

### 冷启动失败与明确重试

六轮冷启动共 **9000 人次**，首次未完成 **6 人次**：5 次登录十秒超时、1 次首页事件读取十秒超时。登录 P95 为 **2.395–3.172 秒**。原始第三轮另有一次 WebSocket 意外关闭，不把整个测试说成“完全零错误”。

首组三轮用于原样复现，轮次之间重置合成数据，没有对其中的 5 个失败人次做逐账号恢复验证。后续恢复场景独立运行三轮：初次分别完成 1499、1500、1500；第一轮保留原有数据库，找到该轮未报名账号，约在开测 **57.91 秒**后模拟用户明确重试。登录、首页、详情、报名、查询确认共耗时 **42.4ms**，最终报名数 1500、名额一致。后两轮没有失败账号，因而没有实际重试，不算成两个额外的恢复样本。

这证明本轮复现的失败账号可在压力后继续正常操作，不代表最早需要等待 58 秒；测试没有测量最小恢复等待时间，也没有验证第一次超时后立刻重试。**当前前端登录不会自动重试，十秒超时后仍需要用户重新点击登录。** 本次不改前端逻辑或业务代码。

### 资源和进程证据

- 整体观测约 **24.57 分钟**，共有 **271 个采样记录**。有效观测内 MySQL、Redis、API 主进程及 worker、后台 worker、Nginx 主进程及 worker 的初始 PID/启动时间保持一致；容器没有重启。
- 父配额及各子容器 `oom`、`oom_kill` 增量均为 **0**。历史父计数 `oom=11, oom_kill=4` 保留，没有归零或把历史事故混入本轮。
- 本轮内存**采样峰值 2155.7MiB（2.11GiB）**。开始与结束的历史高水位同为 2259.5MiB，不能当作本轮精确峰值。
- 约 5 秒窗口 CPU 平均用量的最高采样约 **2.99 核**；这不是瞬时 CPU 峰值，也不是物理单核性能标定。CPU quota 的节流统计保存在资源 JSON 中。
- 有效健康探针 **514 次**全部 HTTP 200，最慢 **168.2ms**。有 **1 次监控采样失败**，只保留了 RuntimeError 类型，具体原因未被保留；前后原进程标识一致，但这个观测缺口不能算成一次成功采样。最初另外 6 个采样点的地址配置错误见下文。
- 冷启动流程中的报名请求因登录/浏览先后完成而分散，不冒充严格一秒报名；上面的已登录集中报名场景单独验证了实际约 0.60 秒发出 1500 个报名请求。

原报告保留失败门槛。`data_correct` 同时包含“数据一致”和“达到全部预期报名人数”，冷启动有未完成学生时它为 false，并不表示名额账已经不一致。逐轮 `data_consistency_pass` 及 `inconsistencies` 才是对应的数据核对证据。

### 交付与结束状态

本次只提交测试工具和证据：资源限制工具新增显式 `--memory-mib 4096`，补充只读进程/健康观测、TEST 合成账号恢复检查。相关 **11 项测试通过**，Ruff 通过。前端保持 `develop / b49264a`，无业务接口兼容变更。

发压进程已结束；测试服务保留 **4 核配额 / 4GiB**，无出口人工限速。生产、Surge、小程序发布均未改动，无 push。真实腾讯云单核性能、公网链路和长期运行仍不在本次验收范围内。


## 复核材料

证据位于 `reports/wired-four-cpu-stability/`。主报告引用每个原始分片的 SHA256；分片以 `.parts.tar.gz` 无损归档，`raw-archives.json` 同时记录归档和成员校验值。进程/健康 JSONL、开始和结束资源快照，以及运行和汇总脚本一并保留。

监控最初误用 `127.0.0.1:18081`，而服务只绑定 `192.168.100.130:18081`，随后修正。最初探针失败作为工具配置错误原样保留，不算服务器故障，也不拿它们证明健康；进程连续性观测不受该地址错误影响。
