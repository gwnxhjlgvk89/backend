# 独立有线 Linux 发压复测

后续已完成逐请求关联与接入路径对照，见 [首页失败与登录超时定位](NETWORK_FAILURE_DIAGNOSIS.md)。本页保留此前的测试结果。

2026-09-28。此次只测试和记录证据，应用代码保持 `547aab2`，前端保持 `b5b1d90`；未部署生产、未改 Surge 日常设置。

## 环境与范围

- 发压机 `192.168.100.20`：Linux、36 个逻辑 CPU、约 24GB 内存；Python 3.11.2，aiohttp 3.13.3，psutil 7.2.2。仅测试进程提高文件描述符上限至 16384，未修改系统配置。
- 发压到测试机 `192.168.100.130` 直接走 `enp6s0`，网卡协商速率 1000Mbps；路由无网关。Mac 只负责 SSH 编排和取回证据，1500 条业务连接不经过 Mac、Surge 或 WireGuard。
- 测试服务父 cgroup 为 `cpu.max=800000 100000`、`memory.max=4294967296`、禁 Swap；4 个 API worker，4 个 Nginx worker。该 CPU 配额不等同于腾讯云 8 核单核性能，部分 rootless 网络辅助进程处于配额外。
- HTTPS 使用测试 CA 验证证书身份，10 秒请求超时；3 个独立发压进程，各 500 个不同合成账号，同一未来时间屏障，0.6 秒计划突发。
- 带宽使用测试 Nginx 私有网络命名空间的 TBF，仅约束响应方向；不模拟公网 RTT 或丢包。TBF 队列参数沿用之前的 32KB burst、2000ms latency，并记录实际流控计数。因此这不是腾讯云公网质量的等价复现。

原始资料见 [wired-linux-8cpu4gb](../reports/wired-linux-8cpu4gb/)，包含路由、依赖版本、资源配额、逐请求分片、流控状态与编排脚本。所有报告仅保存统计和合成数据，不保存密码、登录 Token 或响应正文。

## 验收口径

纯登录测试每个学生新建 TCP/TLS 连接，只登录；完整流程另外建立 WebSocket、获取首页和详情、报名、接收名额与个人状态事件，再持续浏览。两者分别报告，不能用纯登录通过替代完整流程通过。

冷登录后的报名时间会受前序请求影响，不能直接当作 1500 人同时报名的证据。提前登录场景单独核查报名请求实际发出跨度；不只检查计划时间。每轮核对数据库报名数与实际完成数、名额差异、WebSocket 在线数及通知延迟。

本轮每个流程保持约 45 秒，属于短时对照测试。未重复 600 秒稳定性测试、真机、3000 人过载、热点或最后一席测试，也没有确认生产机器容量。

## 分阶段结果

每格为 1500 次请求，均在约 0.60 秒内由发压进程开始。P95 包含 TCP、TLS 及 HTTP 完整响应时间；各阶段分位数不能相加。0Mbps 表示未施加出口限速。

| 出口限速 | 场景 | 成功 | 端到端 P95 / P99 秒 | 应用 P95 秒 |
|---|---|---:|---:|---:|
| 0Mbps | HTTPS 健康检查 | 1500/1500 | 1.160 / 1.173 | 0.00013 |
| 0Mbps | 纯冷登录 | 1500/1500 | 1.204 / 1.229 | 0.02139 |
| 10Mbps | 纯冷登录 | 1500/1500 | 2.637 / 2.714 | 0.03104 |
| 50Mbps | 纯冷登录 | 1500/1500 | 1.288 / 1.308 | 0.02705 |
| 0Mbps | TLS 建连 | 1500/1500 | 1.040 / 1.055 | — |
| 10Mbps | TLS 建连 | 1500/1500 | 1.609 / 1.660 | — |
| 50Mbps | TLS 建连 | 1500/1500 | 1.048 / 1.059 | — |

所有七组均无超时或连接重置。这与此前 Mac 经 Surge/WireGuard 发压时的失败形成明确对照；并不精确区分 Surge 保护、隧道及旧发压端的各自贡献。独立有线路径已使纯冷登录恢复到 5 秒目标内。

`login` 为冷登录完整流程，`ready` 为提前登录后统一浏览、报名。首页统计合并 bootstrap、event_bootstrap 和 burst_bootstrap 的原始请求，避免遗漏由活动事件触发的首页加载。实际报名请求头跨度大于一秒的轮次没有满足严格开抢负载，不能因为全部成功而授予容量通过。报告保留脚本原始门槛，并额外校验实际请求头时间。

10Mbps 冷登录三轮登录均无失败；后续首页分别出现 18、17、30 次 `ClientConnectorError`，完整流程未通过。现有驱动仅保存异常类别，未记录底层 errno，不能精确断言这些连接失败的唯一原因。三轮数据库均与成功报名数一致，名额差异列表为空；原始 `data_correct` 综合门槛未过是因为没有达到预期的 1500 人，并非已发现数据错乱。

10Mbps 冷登录完整流程三轮 TBF 累计丢包 11844，提前登录场景三轮累计 10063。已返回响应的应用登录 P95 约几十毫秒，其端到端耗时的大部分在应用计时之外。失败请求没有 Server-Timing，不能用成功请求的应用耗时替它们下结论。TBF 排队及丢包是本测试设置下的直接证据，不是腾讯云公网的实测丢包率。已有 JSON gzip 压缩，响应字节统计是解压后的业务体，不能直接拿它除以 10Mbps 推算线上耗时。

50Mbps 限速队列记录丢包为零，浏览和通知明显改善，但登录第二、三轮分别有 5、7 次十秒超时；第三轮另有一人首页失败、一条 WebSocket 意外关闭。12 次登录超时均记录了连接完成及请求头发出，随后未收到响应头。客户端写出请求并不能证明 API 已收到它；现有证据不能进一步区分转发链路、API 排队或响应传输。详见 `login-timeout-analysis.json`。宿主机测试端口监听队列上限与 somaxconn 均为 4096，没有仅凭默认小队列作出根因判断。

因此：独立 Linux 发压已绕过 Surge/WireGuard 干扰，10Mbps 全流程存在明确队列压力，50Mbps 仍有少量长尾超时。本轮没有达到完整容量验收，也没有证据支持直接升级 CPU 或断言增加带宽即可彻底解决问题。后续应在隔离环境补齐不含凭据的请求 ID、Nginx upstream 时序与 API 时序关联，并对宿主机和容器网络分别采样，定位这 12 次响应等待的来源；无需先改业务逻辑。
