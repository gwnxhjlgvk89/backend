# 完整学生流程压测与资源阶梯

## 范围

仅运行隔离 `club-capacity-test` 容器、合成load账号；生产只读。压测机与服务机分离。默认每请求10秒超时，与前端一致。1500学生在0.6秒计划窗口内开始，各自登录→bootstrap→WebSocket→详情→服务端开放时间→报名；不等待所有登录完成才进入下一阶段。事件驱动重同步、在线60秒核对、20秒心跳、20–40秒浏览以及超时后查结果/一次同键重试一起计入。

模式：`login`全员同步密码登录，`ready`提前登录后集中浏览/报名，`mixed`1200已登录与300临近开放登录交错，`reconnect`集中连接恢复。每种模式可配均匀、热门和最后一席，支持冷/热目录缓存、连续三轮和600秒活跃运行。测试界面渲染与真实手机仍按用户要求暂缓。

```sh
.venv/bin/python scripts/load_journey.py --url http://TEST_IP:18081 --mode login --rounds 3 --hold-seconds 600 --report reports/UNIQUE-NAME.json
```

报告拒绝覆盖已有文件；不记录令牌/密码/用户完整资料。逐接口统计所有请求的P50/P95/P99/最大值、服务端P95、状态、字节、真实发送跨度及每秒到达数，并记录未完成学生。对照数据库报名/剩余数，不以只剩少量成功用户后的低延迟宣称达标。WebSocket消息触发的请求一并统计。

用户2026-09-28最新调整为登录P95≤4秒、报名P95≤3秒；交互读请求也按P95≤3秒判读；报名P99仍≤5秒。通知按3秒目标单列；1500容量不允许用429/503消化正常负载。若用户希望“每个请求最多3秒”，需另行明确更严格的最大值门槛，P95不能代表最大值。

## 首轮基线（优化前应用2ab9cc6）

`journey-baseline-login-4cpu-10mbps.json`：4CPU额度、3000MiB、10Mbps。1500人登录实际发出跨度0.8485秒，322个200、1178个503；仅314人完成后续报名。它是失败基线，不能用314人的报名P95约2秒声称1500人通过。

流控证据：`journey-baseline-egress-before/after/restored.json`，仅测试容器lo的8080响应受限。源代码发现登录在密码计算等待期间占用主数据库连接，造成连接池竞争；后续先修复此软件问题，再讨论硬件。

## 硬件判读原则

保持4CPU/3000MiB/10Mbps先优化，不降低密码哈希成本或跳过鉴权，不以虚构低成本账号、放宽超时/隐藏失败、大量拒绝请求代替性能。确认具体瓶颈后分别改变CPU或出口带宽，内存只在实测不足时增加。每个资源档位记录父cgroup实际值、TBF实际计数及应用指纹，单变量比较。

Ryzen5900X额度只代表这台机器上的资源档位，不等于EPYC云机相同vCPU。没有同规格独立云机实测前，配置建议只能是候选及最低吞吐要求，不能声称购买某个核数就能达标。所有原始失败轮次保留；不会自动购买云机或在生产执行压力基准。

## 2026-09-28：软件优化与更严格的驱动

- 登录密码计算移到数据库会话之外，保留锁内二次账号状态/hash核对；冷目录缓存同一进程合并回源；Nginx压缩JSON。
- 前端配套 `46793a8`：报名成功直接使用返回值、个人报名事件只查结果、30秒内切页复用初始化数据。
- 全员名额广播合并间隔改为1.5秒，个人/会话仍250ms；通知目标3秒，最终仍需实测判定。
- 密码先测19MiB/2轮，进一步对比OWASP列出的四种配置。8CPU额度单项基准中7MiB/5轮/8线程约555次/秒，19MiB/2轮/8线程约264次/秒；据此为新账号采用7MiB/5轮，已有较强参数不自动降参。基准不是HTTP测试，不能直接外推云机核数。
- 驱动现在为每位学生建立独立HTTP连接池，开启HTTPS并校验指定测试CA；记录脚本指纹、应用指纹、密码任务并发度、实际CPU/内存和宿主压力。SSL私钥仅存测试机忽略目录 `.local/tls`，不提交。
- `ready`/`mixed`后续轮次复用已登录学生的有效会话，再重建WS和初始状态；全员密码登录模式每轮仍实际验密。每轮数据重置、错误和未完成学生单独统计。最终名额版本按每位学生的实际快照/推送核对，不能只统计收到过的中间事件。
- `run_journey_case.py`保存限速前后/恢复证据，每轮结束撤销测试流控并恢复4CPU额度。启动失败不当成性能失败；首次8CPU启动尚未就绪的预检日志/流控文件保留，实际结果带`-r1`后缀。

TLS复现：运行 `deploy/prepare-test-tls.py --host TEST_PRIVATE_IP`，compose同时加载 `compose.test.yml` 与 `compose.test.tls.yml`，将公开测试证书复制至压测机，驱动传 `--ca-cert`，使用18082端口。此为真实TLS计算开销与私有CA校验，不代表微信已接受此自签测试域名，也不模拟公网RTT/丢包。

阶段性失败记录：

- `journey-readopt-ready-4cpu-10mbps.json`：三轮每轮1500报名、无超卖/重复，P95为3.3322/3.2431/3.1396秒；原1秒广播版本在10Mbps下仍未通过。
- `journey-argon-login-4cpu-10mbps.json`：19MiB配置、旧共享HTTP池，748人登录200；未通过。
- `journey-https-login-4cpu-10mbps.json`：19MiB配置、独立池/TLS、730人登录200；未通过。

查询进一步优化：8CPU/20Mbps全员登录成功后，仍有身份查询连接等待超时。将每进程主池从15+5改为15+3、预留读池从2改为4，总预算仍为98/150；然后把同一瞬间的账号ID/用户名读取合并成最多128项、2ms窗口的SQL批次。结果只交给当前等待请求，不跨批次缓存，不跳过停用/会话版本校验；报名和管理写入仍在各自事务里重读并锁定。队列有上限，取消和关闭会清理等待者。51项后端回归通过，包括更新账号后立即读到新状态、批量查询减量、取消隔离和队列上限。

## 最新测量边界与严格登录目标

用户最新明确：1500人同步登录放宽至P95≤4秒；报名P95≤3秒、P99≤5秒保持。此前3秒门槛的原始记录保留，新门槛另行判读。`login`每轮重新创建每位学生的HTTP池，包含冷TLS连接；`login_warm`仅提前建立TLS，仍对1500个独立账号逐一验密，属于耗时定位，不能替代冷启动登录验收。报告同时记录请求开始跨度和HTTP头实际发送跨度。客户端端到端延迟包括TLS，不用较小的Server-Timing替换。

`ready`和`mixed`允许复用已有连接（HTTP空闲保持60秒）；此前15秒保持的失败样本仍保留。`cold`仅指目录Redis缓存清空，不代表数据库buffer pool、操作系统页缓存或整个服务重启。

容器配额只约束CPU时间，不固定物理核；宿主有12物理/24逻辑线程。发现rootlessport/slirp4netns处在pod配额之外，新采样记录同用户网络辅助进程的CPU/RSS并明确可能共享，不能将其全部归入本系统。此部署还含rootless转发额外开销，与生产systemd网络路径不同。因此不把16CPU额度称作“16核云机”，也不据其结果按比例推导生产核数。

测试数据：3000个独立盐的Argon2id账号，42个社团，详情包含约680个中文字符；不含社团封面图片/CDN下载，也不含首次强制改密。旧bcrypt账号首次成功登录还会追加安全哈希升级，不能用新账号压测承诺旧账号首登性能。初始化密码和活动开放应分开安排，正式名单导入默认仍强制改密，不绕过规则。

原始结果、脚本与应用指纹都保留。`scripts/check_journey.py`只读汇总各报告及配套流控证据，显式区分局部场景通过、完整验收和硬件等价；不修改原报告或以单轮通过授予生产容量结论。

## 多进程发压复核

`run_journey_case.py --processes 3`将独立学生划分给3个Python进程，每人仍有自己的账号、HTTP池与WS。协调器单独重置测试数据、清空目录缓存、设置服务端开放时间，再用同一绝对时间屏障释放请求。没有把1500人拆成先后执行的3批。

每轮保留 `.parts/` 中逐请求的状态/延迟/实际发出时间与子进程资源记录；合并原始样本后重新计算分位数，不能对三个P95取平均。数据库最终占位与三个互不重叠账号分组的成功确认数核对。每轮全冷登录新建三个进程及全部HTTP池；预建TLS模式只用于对照。协调器失败会终止其子进程，wrapper继续恢复流控/CPU配额。

此改进降低单个Python事件循环集中处理1500次TLS的干扰，仍不等于1500台真机，也不能替代公网网络或云机等价验证。正式门槛始终以全部用户、全部请求、实际发送跨度和端到端延迟判定。

## 首页读查询进一步合并

完整链路中每个bootstrap原来单独查询活动、个人报名、收藏和名额，同步首页/WS重同步会重复这些SQL。新增有界批量读取：每进程最多128个用户、2ms聚合窗口，用4次查询组装各自的个人结果和公共快照；不跨批次保存结果。身份鉴权仍独立执行，报名事务规则不变。回归覆盖30人只执行4次查询、收藏/报名不串用户，以及暂停活动/名额更新后下次请求立即读到新值。全部56项后端测试通过。

2026-09-28 600秒混合报告 `journey-mixed-600s-8cpu-20mbps.json` 是此次首页批量查询之前的应用指纹：51,588次测量请求，1500/1500完成与在线，零异常断连，报名P95=1.8098秒，通知P95=0.5753秒，稳态读取P95=0.0955秒；末六个pod内存样本1342.2/1344.9/1344.9/1341.0/1341.9/1345.0MiB。此历史稳定性结果不自动授予改动后版本验收。

## 监控链路与密码耗时拆分

登录等待需要区分原生计算与事件循环/线程调度：新增 `club_password_native_seconds` 在受限线程内测量函数本体，原 `club_password_execution_seconds` 明确包含调度时间。HTTP监控直接包装ASGI响应头，保留请求ID、Server-Timing、no-store和脱敏结构化日志，消除逐请求任务/流桥接；不删除指标或跳过鉴权。专项验证错误响应的请求ID与脱敏、普通响应和WebSocket透传。

只读路由检查确认当前独立Mac发压经Wi-Fi en0，所有已有有线接口未连接。曾观察到路由RTT估计44ms；这是该时刻内核估计，不是固定注入延迟。已请求可用有线发压路径；用户表示线上资源可灵活升级、现阶段不需要追问云规格。暂不把冷TLS长尾全部归因于服务器CPU，也不宣称任何核数已经满足公网容量。

## 首次连接流量模型修正

发现原前端先bootstrap、再连接WS，首次resync会再次下载bootstrap；后端查询优化后这仍增加网络开销。前端改为先发起WS（票据后等待握手最多1.5秒），再初始化，resync与初始化共享进行中的请求。迟到resync不跳过，WS失败仍回退HTTP。压测新增 `connected_first` 模型并设为默认，历史 `lean` 原样保留以复现旧请求顺序；不把请求减量称作相同流量下的CPU扩容收益。

本轮用户明确暂时没有有线发压条件，要求继续完成现有环境测试；后续结果继续标注Wi-Fi、rootless网络与CPU时间额度边界，不再等待提供云机型号或有线设备。
