# 首页失败与登录超时定位（2026-09-28）

## 结论与可信边界

已把本次复现的错误定位到建连和回包传输链路：没有发现这些错误由首页查询或登录业务处理过慢造成。测试使用 rootless Podman 发布 TLS 端口，并在 Nginx 网络命名空间的 loopback 上施加 TBF 限速；这个组合会给冷连接和回包增加额外压力。绕过前端 TLS 的 rootless 端口转发、将限速移到 HTTP 后端段后，连续三轮每轮 1500 人均完成流程。

这是故障层级定位与替代路径验证，尚未证明 rootlessport 内部的某个具体实现缺陷。对照改变了 TLS 终止位置和限速所在链路，不能仅凭它区分二者的全部贡献；也不能把此结果当作 10Mbps 公网完整 HTTPS 容量验收。

应用业务代码仍为 `547aab2`，API/数据库/报名事务未改。现有证据不支持为了这两种异常立即增加 CPU 或重写登录逻辑。

## 逐请求证据

在发压请求中增加随机十六进制 `X-Load-Request-ID`，记录错误 errno、连接耗时、发出请求头时间和 API request ID。临时 Nginx 日志将这个 ID 与 API 返回的 `X-Request-ID` 关联，记录上游建连、响应头、响应完成耗时；没有记录 Authorization、正文、查询字符串或 WebSocket 票据。日志的请求处理时间与上游时序含义见 [Nginx access log 文档](https://nginx.org/en/docs/http/ngx_http_log_module.html)和 [upstream 变量文档](https://nginx.org/en/docs/http/ngx_http_upstream_module.html)。

### 首页失败

保留原接入路径并施加 10Mbps 限速后，复现 34 名学生首页失败：9 次 `ClientConnectorError`、25 次十秒超时。

- 其中 25 个失败请求没有在 Nginx 请求日志中出现，主要卡在建连阶段；未取得底层 errno 的请求不臆测成“连接被拒绝”。“无请求日志”不等于没有收到任何 TCP/TLS 字节。
- 另外 9 个超时请求已到达 API，并在 **8–15ms** 内返回 200；Nginx 完整写出响应，但客户端没有及时取得结果。
- 此轮没有 API/Nginx 5xx、数据库名额差异或新增 OOM；只统计成功报名学生时数据一致，但只有 1466 人完成，不算容量通过。

对应 API 脱敏记录为 `api-failure-matches.json`，完整映射保存在 `summary.json` 的 failures 中。

### 登录超时

在原接入路径的 50Mbps 对照中，复现一名学生登录超时。其关联 ID 为 `1210262672684724abf453e569102a46`：

- 客户端约 2.264 秒完成连接并发出请求头，10 秒时超时。
- API request ID 为 `bf6ad030e7c841539799e8c3647ab135`，业务处理 **41ms，HTTP 200**。
- Nginx 上游与整体请求耗时约 **42ms**，状态 200、完成标记 OK、写出 623 字节。

Nginx 写出并不意味着最终客户端已收到：此路径的下一跳还有容器端口转发、限速队列和主机网络。这条匹配记录将等待范围缩小到了应用处理之外；不能用它证明所有历史超时都是同一个底层缺陷。

## 对照实验

独立有线发压机仍为 `192.168.100.20`，目标为 `.130`，全程保持父配额 8CPU/4GiB。3 个独立发压进程、1500 个不同合成账号，计划 0.6 秒发起冷登录，完整浏览/报名/通知流程约 45 秒。无生产请求。

临时替代路径：客户端 HTTPS → 宿主机网络中的临时 Nginx → 原 TEST Nginx 的 HTTP 入口 → 原 API。原组件仍在，额外增加 4 个入口 worker，仍共用 8CPU/4GiB 父配额。**10Mbps 只限制后端 HTTP 段，TLS 握手不在限速范围内。** 此设置用于拆分故障层级，不能与原有全 HTTPS 限速结果作同条件性能排名。

| 对照 | 完成学生 | 登录 P95 秒 | 报名 P95 秒 | 通知 P95 秒 |
|---|---:|---:|---:|---:|
| 原 TLS 转发 + 10Mbps | 1466/1500 | 3.767 | 2.040 | 3.962 |
| 原 TLS 转发 + 50Mbps | 1499/1500 | 3.743 | 1.430 | 1.368 |
| 原 TLS 转发，移除限速 | 1500/1500 | 3.375 | 1.441 | 1.639 |
| 临时直连 TLS / 512MiB 初测 | 1500/1500 | 3.393 | 2.226 | 1.969 |
| 临时直连 TLS / 重复 1 | 1500/1500 | 3.544 | 2.250 | 1.938 |
| 临时直连 TLS / 重复 2 | 1500/1500 | 3.489 | 2.154 | 1.988 |
| 临时直连 TLS / 重复 3 | 1500/1500 | 3.479 | 2.188 | 1.908 |

三轮重复均零请求错误、1500 条 WebSocket 在线、最终名额版本完整、无名额差异、无新增 OOM。但报名实际请求头跨度约 4.18–4.28 秒，未达到严格的 1500 人一秒报名负载；没有新的 600 秒稳定性、真机或生产验收。上述压测驱动尚未启用前端新增的读取重试，不把替代链路的成功归功于前端修复。

初次临时入口误设 128MiB，发生 4 次 worker OOM kill，产生大量异常；该实验明确标记 `invalid_for_attribution`，原始数据保留。修正为与原 Nginx 相同的 512MiB 后，整个临时入口内存峰值约 207MiB，OOM kill 计数仍为历史值 4，没有新增。补齐 OOM 核验为观察窗口的计数增量，并拒绝计数重置、缺失样本和单样本证明，避免历史诊断事故使后续报告永远失败，也不隐藏新 OOM。

## 已完成的修复与验证

前端提交 `b49264a`：GET 读取遇到网络传输错误时随机等待 0.5–1 秒，最多重试一次；同账号同路径仍合并请求，切换账号后不重试。HTTP 业务错误不重试，登录、报名等写操作不自动重放。此改动减少偶发网络故障直接变成首页错误的概率，不宣称能修复持续断网；最坏读取等待约 21 秒，必须保留首次失败与最终恢复的不同口径。

前端 17 项测试通过，覆盖重试合并、上限、账号切换、写请求不重放；类型检查和显式测试 HTTPS 地址的微信小程序构建通过。无发布、无真机验收。

后端增加 TEST 专用 `deploy/trace-test-requests.py` 与发压关联字段；12 项相关测试及 Ruff 通过，包括生产目标拒绝、日志敏感字段排除、统计和 OOM 增量判定。后端业务无需配套接口变更。

## 后续与清理

生产准备应沿用已计划的原生 Nginx/systemd 接入方式；最终带宽验收需要覆盖完整 HTTPS 链路的隔离限速环境，避免把内部 rootless 回环链路直接当作公网。若要进一步定位到具体转发器实现，需要对失败连接进行双端 TCP 时序关联；当前不凭猜测修改 sysctl、替换认证机制或升级硬件。

所有本轮发压进程已结束，临时入口容器已移除，临时日志配置恢复，出口 qdisc 回到 noqueue。测试服务保留 8CPU/4GiB，生产和 Surge 未改。诊断 JSONL 已压缩归档，原始分片无损归档并逐成员核对 SHA256；见 [证据目录](../reports/wired-diagnosis/) 和 `raw-archives.json`。复核原始请求时先解压相应 `.parts.tar.gz`，再运行保存的汇总脚本。
